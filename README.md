# IST3134 - Big Data Analytics in the Cloud
### NYC Yellow Taxi Trip Analysis: AWS Spark (EMR) vs Python (pandas) Comparison

A comparative Big Data Analytics project analysing six months of NYC Yellow Taxi trip records using two parallel pipelines - one built on **Apache Spark running on an AWS EMR cluster**, and one built on **conventional Python (pandas + scikit-learn)** - to answer real analytical questions about taxi demand, fares, and payment behaviour, while directly measuring how a Big Data platform compares to a single-machine approach at this scale.

---

## Problem Statement

This project processes NYC TLC Yellow Taxi trip records to answer four questions:

1. How do trip volume, average fare, and average trip duration vary by pickup zone, hour of day, and day of week?
2. How does payment method relate to trip volume and tipping behaviour?
3. What are the dominant borough-to-borough travel flows across the city?
4. Can trip fare be predicted from ride characteristics (trip distance, passenger count, pickup hour, and pickup zone)?

Each question is answered twice - once via the Spark/EMR pipeline, once via the Python pipeline - so that, alongside the analytical findings, the project produces a direct, evidence-based comparison of runtime, memory usage, and scalability between the two approaches.

## Dataset

- **Source:** [NYC TLC Trip Record Data](https://www.nyc.gov/site/tlc/about/tlc-trip-record-data.page)
- **Coverage:** Yellow Taxi trip records, October 2025 - March 2026 (6 months)
- **Format:** Apache Parquet, plus the Taxi Zone Lookup CSV (zone ID -> borough/zone name)
- **Scale:** 23,992,355 raw rows -> 16,803,729 rows after cleaning, 20 columns per record

Raw dataset files are **not committed to this repository** due to size - download them directly from the TLC link above, or via the OneDrive link in [Resources](#resources).

## Pipeline Overview

Both pipelines implement the same five logical stages against the identical dataset:

1. **Load** - read raw Parquet trip data (S3 for Spark; local/Colab disk for Python)
2. **Clean** - filter invalid fares, distances, passenger counts, and unrealistic trip durations; derive `trip_duration_min`, `pickup_hour`, `pickup_dow`
3. **Join** - attach pickup/dropoff borough and zone names via the Taxi Zone Lookup table
4. **Aggregate** - zone x hour, day of week, payment type, and borough-to-borough flow
5. **Model** - Linear Regression predicting `fare_amount` from `trip_distance`, `passenger_count`, `pickup_hour`, and `PULocationID`

Each pipeline independently times every stage and writes a metrics CSV; `BDA_Spark_vs_Python_Comparison.ipynb` aligns the two (accounting for differing stage granularity between platforms) into `combined_metrics.csv`, used to produce every comparison table and chart in the report.

## Running the Pipelines

### AWS Spark (EMR)

```bash
# Upload data to S3
aws s3 cp yellow_tripdata_2025-10.parquet s3://<your-bucket>/dataset/
# ...repeat for each month, plus taxi_zone_lookup.csv

# On the EMR primary node
spark-submit --master yarn --deploy-mode client \
  --num-executors 2 --executor-memory 4g --executor-cores 2 \
  spark_pipeline.py
```

Cluster used for this project: 1 primary + 2 core nodes (m5.xlarge). See the full report (Section 3.3) for cluster configuration notes and troubleshooting.

### Python (pandas)

Open `pandas_pipeline.ipynb` in Google Colab (or a local Jupyter environment), point `input_dir` / `zones_path` at your local copy of the dataset, and run all cells. Produces `metrics_python.csv` and the aggregated Parquet outputs.

### Comparison

Once both `metrics_spark.csv` and `metrics_python.csv` exist, run `BDA_Spark_vs_Python_Comparison.ipynb` to produce `combined_metrics.csv`, the stage-timing table, model accuracy table, and comparison charts.

## Key Results

| Metric | Spark (EMR) | Python (pandas) |
|---|---|---|
| Raw row count | 23,992,355 | 23,992,355 |
| Clean row count | 16,803,729 | 16,803,729 |
| RMSE | 13.379 | 13.457 |
| R² | 0.458 | 0.451 |
| **Total runtime** | **122.75s** | **148.15s** |

Spark outperformed Python overall (1.21x speedup), with the advantage concentrated almost entirely in aggregation-heavy stages (29x-69x faster), while lighter stages (data load, zone join, model evaluation) were actually faster on Python due to Spark's per-task coordination overhead. Full analysis, discussion, and business insights are in the report.
